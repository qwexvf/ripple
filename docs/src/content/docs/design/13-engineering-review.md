## 1. 結論

1. **ツールの設計と測定文化は、この規模のプロジェクトとしては例外的に良い。** 特に `docs/12-dogfood-log.md` は、自分の headline 数値を自分で撤回した記録が残っている点で資産。
2. **一方で、外向きの数字と用語が実装より強い。** `bug_density` は defect density ではなく fix コミット率、`untested` はカバレッジではなくエッジ不在、risk 式の 6 項のうち 2 項は何も populate していない。名前が実装より大きいと、最初に気づいた読者はそこで一度信用を引く。
3. **最大の訂正は recall の数値がリポジトリ依存だということ。** 「静的グラフは変更カップリングの 93% を見落とす」は、あるプライベート Web アプリの値。hono で leakage-free に測ると **静的のみで 57.5%** 取れる（§5）。数値はツールの性質ではなくコードベースの性質で、この一文はどちらのリポジトリでも「ツールの主張」として使えない。

## 2. 用語監査

「エンジニア向けとして妥当か」への答え: **英語の技術用語の選択はほぼ妥当**（`churn` / `fanout` / `IR` / `leakage` / `holdout` / `MCP` / `stdio JSON-RPC` は文献・実務の標準語）。問題は 2 種類に分かれる — **(A) 実装より強い名前**、**(B) 日本語化の失敗**。

| # | 用語 | 実装の実体 | 種別 | 問題と推奨 |
|---|---|---|---|---|
| 1 | `bug_density` | fix/revert パターンにマッチしたコミットの割合（`crates/overlay/src/lib.rs:246`, `ratio(m.fix_commits, m.commits)`） | A | 文献の defect density は「欠陥数/KLOC」。別物なのに同名。`docs/06` 自身が heuristic と認めている。**→ `fix_commit_ratio` に改名**。改名しないなら出力の隣に必ず定義を出す |
| 2 | `untested` / 未テスト | `Tests` エッジが存在しない（`test_proximity` の裏返し） | A | 「テストが無い」と読まれる。実際は「このシンボルを参照しているテストを ripple が見つけられなかった」。解決漏れでも同じ表示になる。**→ `no test reference` / 「テスト参照なし」** |
| 3 | `ownership` | `percentile(1.0 / author_count)`（`crates/overlay/src/lib.rs:247`） | A | 名前から方向が読めない。値が高い = 著者が少ない（集中）。式は `(1 − ownership)` なので**「著者が多いほど高リスク」**（coordination cost の解釈）。ところが `docs/06-risk-and-queries.md:15` のコメントは "author dispersion; low = bus-factor risk" で、bus factor（著者が少なすぎる方が危険）と読める。**式とコメントが逆を向いている。** → `author_concentration` に改名し、どちらのリスクをモデル化しているのか 1 行で明記。単一著者リポジトリでは全ファイルが同値になり percentile が 0 に潰れる既知の性質（`docs/12:157-162`）も併記 |
| 4 | `complexity` / `test_proximity` | **未実装**。`blend` が「corpus 内で分散のない項」を落とす（`crates/overlay/src/lib.rs:389-395`） | A | 式には載っているが動いていない。実際に出るのは `churn` / `bug_density` / `ownership` / `fanout` の 4 項。**→ 式を出すときは未実装項を明示** |
| 5 | `逆拡散` | 減衰付きの逆方向到達（重み付き reverse reachability） | B | 2026 に「拡散」は拡散モデルを想起させる。グラフ探索の語としても非標準。**→ 「重み付き逆方向探索（距離減衰付き）」** |
| 6 | `ステイルネス` | インデックスが古くなること | B | 不自然なカタカナ。**→ 「インデックスの陳腐化」** |
| 7 | `所有が薄い` | `ownership` が低い = 著者が多い | B | 日本語として両義的（著者が少ない、とも読める）。#3 と同じ根。**→ 「著者が分散しているほど高リスク」** |
| 8 | `予算` | トークン予算 | B | 単独では予算管理と読める。**→ 初出は「トークン予算」** |
| 9 | `blast radius` | 変更影響分析 | — | SRE / Terraform 由来で、SE の標準語は change impact analysis (CIA)。`docs/02` は意図的に使っており、キャッチとしては有効。**→ 初出で CIA を併記すれば問題なし** |
| 10 | `co-change` / 論理結合 | 同一コミットで一緒に変わる関係 | — | 文献は logical coupling / change coupling / evolutionary coupling。CodeScene の語彙は logical coupling（`docs/01:67`）。ページで併記済み。**維持** |
| 11 | `score` / `priority` | ranking key（`impact_weight · risk`、`hunk risk · downstream`） | — | 語が場所ごとに違う。**→ どちらかに統一** |
| 12 | recall のみ提示 | 適合率は非公開 | A | 「recall 40%」だけでは判断不能。co-change エッジは precision を落としやすい種類の信号なので、engineer は必ず「precision は？」と聞く。Elixir 側は LSP oracle で 87.9%（144/165 一致）を測れている（`docs/12:113-117`）が、**TypeScript の call graph precision は未計測**（golden fixture のみ、`docs/v0-plan.md:73`） |

**まとめ**: 用語そのものは分かる人向けに正しく選ばれている。直すべきは「実装より大きい名前」4 つ（1〜4）と「日本語化の失敗」4 つ（5〜8）。9〜11 は運用で足りる。12 は用語ではなく測定の穴。

## 3. ロール別評価

### 3.1 Programmer（日々コードを書く人）

**効いているもの**

- `search` が候補を**構造化して**返す。hono で `search { query: "getPath" }` は 9 件を `kind` + `qualified` + `module` 付きで返し、うち 4 件は別クラスの同名メソッド（`EventV1Processor.getPath` / `ALBProcessor.getPath` …）。grep は 9 箇所を平坦に出して終わるので、この差は実作業でそのまま効く。
- `impact` が `via`（エッジ種別）と `depth` を付ける。`ChangesWith` で来た行は「静的に辿れないが一緒に直す場所」であり、これは他のツールが出せない。
- `{shown, total}` で切り捨てを申告する。エージェントに使わせるとき、黙って切られるより桁違いに扱いやすい。

**引っかかるもの**

- **言語ごとの Tier 2 品質差が大きい。** Rust は path call 解決がつい最近入るまで `impact` が 0 hits だった（`docs/12:184-213`）。Elixir は **arity を区別しない**ので `changeset/1` と `changeset/2` が同一視される（`docs/12:120-123`）。「言語追加は 1 フォルダ」はシンボル抽出までの話で、呼び出し解決はそこから先。
- **`reindex` 忘れが黙って間違った答えになる。** CLI/MCP に陳腐化検出が無いので、編集後に `impact` を打つと古いグラフのまま返る。
- **履歴が短いと co-change が学習できない。** `--commits 300` では training 148 コミットから usable pair が **15 個**しか出ず、数値は「モデルが悪い」ではなく「学習データが枯れている」（`docs/12:26-30`）。今回の hono `--commits 50` でも trained pairs は 90。小さいリポジトリや浅い clone では co-change 側は実質無効と考えるべき。

### 3.2 Lead Engineer（導入と保守を負う人）

**効いているもの**

- **劣化を隠さない設計。** git が無い / shallow clone では overlay が空になり、risk は complexity + 静的 fanout に縮退することを明示する（`docs/06:41`）。`eval` は 0 pair のとき「0.0%」ではなく「評価対象が無い」と言うよう直されている（`docs/12:235-251`）。この手の「黙って 0 を返さない」実装は運用で価値が出る。
- **決定性の担保。** ランキングは `impact_weight` → `risk` → `symbol_id` の全順序で並べ、並列や float で順序が動かないと明記（`docs/06:66`）。CI で比較するなら必須の性質。
- **層の分離が実際に守られている。** store は trait 越し、探索は RAM 上、`GraphStore` の裏を差し替えれば済む形（`docs/04`）。
- テスト 106 件、契約テスト（`crates/store/tests/contract.rs`）、golden fixture、LSP クライアントの統合テストあり。

**引っかかるもの**

- **CI が存在しない。** `.github/workflows` が無い（実測）。README と PROGRESS が謳う「clippy 0 warnings / tests green」は**手動保証**。外部から入る人間にとって、これは「壊れているかどうかを自分で確かめないと分からない」状態。まず入れるべきはこれ。
- **GitHub Action も無い**ので、PR レビューに使うなら `ripple index` + `ripple review --json` を自分のワークフローに書く。出力を PR コメントに落とす部分は各自実装。
- **TypeScript の precision が未計測。** ripple の主戦力は TS なのに、精度の数字があるのは Elixir 側（LSP oracle 87.9%）だけ。`eval --oracle lsp` を TS でも回せる設計にはなっている（`docs/11`）ので、やれば埋まる穴。
- **weights が手設定。** `W_CHURN 0.4 / W_BUG 0.4 / W_OWN 0.2` はラベル付きデータに当てていない（`docs/12:176-177`）。導入先ごとに効き方が変わる前提で見る必要がある。
- 作業が未コミット（`crates/cli/src/verify.rs` が untracked、`main.rs` / `store/lib.rs` に変更あり）。評価時点のスナップショットとしては動くが、外部が clone した状態と手元が違う。

### 3.3 Tech Leader（投資判断をする人）

**効いているもの**

- **差別化の言明が具体的で、競合調査が一次情報に当たっている。** `docs/01` は競合のバイナリや MCP スキーマを実際に叩いて確認した記録になっている（例: codebase-memory-mcp が C 実装であることを `.comment` セクションで確認）。この水準の landscape doc は珍しい。
- **対 CodeScene の主張は維持されている。** 関数粒度 + MCP インターフェース + OSS。CodeScene は統計のみで関数を指せない（`docs/01:67`）。
- **精度を外部から借りる逃げ道が設計済み。** LSP を Tier 2 の精度層に置き、遅いサーバをクリティカルパスから外す設計（`docs/11`）。「自前で全言語の解決器を書く」に投資しない判断は妥当。

**引っかかるもの**

- **当初の売り文句は、測り直したら小さくなった。** 「静的グラフ + co-change の融合」による recall lift は、holdout 前は約 34 pt と主張されていたが、leakage を除くと **3〜6 pt**（`docs/12:11-36`、および §5 の実測）。`docs/11` は既に「call-graph coverage が binding constraint」に結論を修正済み。**外向きの物語がまだ追いついていない。**
- 従って、投資の軸は「co-change で余分に見つかる」ではなく **(a) cross-service / cross-repo を 1 回の探索で跨げること、(b) 予算付きでエージェントに渡せること、(c) 理由付きのランキング**に置き直すべき。これは実装が実際に持っている強みで、競合が持っていないものと一致する。
- **導入リスクは言語カバレッジ。** 4 言語（TS / Elixir / GraphQL / Rust、`crates/lang/src/lib.rs:88-94`）で、うち呼び出し解決が実用水準にあるのは TS と Elixir。導入先の主要言語が外れていると価値が出ない。
- **名前の過大主張は、この種のツールでは致命傷になりやすい。** リスクを数値で出す製品は、数値の定義が実装より大きいと分かった瞬間に「他の数字も盛っているのでは」と疑われる。§2 の 1〜4 は優先して直す価値がある。

## 5. 今回の実測ログ（再現手順つき）

release ビルドで公開リポジトリに対して実行。

```
git clone --depth 1 https://github.com/honojs/hono && cd hono
git fetch --depth 400 origin                 # co-change には履歴が必要
cargo build --release && ripple index .
```

| 項目 | 実測値 |
|---|---|
| index（cold, release） | **0.47 s** — 378 ファイル → 10,226 node / 9,653 edge（co-change 110、dependents 持ち 1,284） |
| index（warm, 変更なし） | **0.33 s** |
| index（debug ビルド） | 4.2 s — 参考。公開する数字は release で取ること |

`ripple eval` の held-out 結果:

| test / training commits | pairs | static のみ | co-change のみ | 融合 | lift |
|---|---|---|---|---|---|
| 50 / 365 | 113 | **57.5%** (65) | 31.9% (36)（trained pairs 90） | 63.7% (72) | **+6.2 pt** |
| 100 / 293 | 232 | 56.0% (130) | 25.9% (60)（trained pairs 68） | 60.8% (141) | **+4.7 pt** |

**この表が P1 の根拠。** 同じ `eval` を別リポジトリ（プライベートな TS Web アプリ）で回すと static は 6.5%、hono では 57.5%。**静的エッジの recall はコードベースの構造で 1 桁変わる**ので、どちらの数字も「ツールの性能」として提示できない。提示できるのは「co-change の held-out lift は概ね 3〜6 pt」と「その値も training pair 数に強く依存する」という 2 点。

`review` の実出力（同リポジトリ、`HEAD~5`）:

```
101.34  header (src/request.ts)                — high churn (0.93), 142 downstream, untested
 16.62  getNextAcceptValue (src/utils/accept.ts) — high bug-density (0.62), 18 downstream, untested
  2.96  getCSPDirectives (…/secure-headers.ts)  — high bug-density (0.62), high churn (0.66), 1 downstream, untested
```

1 位と 6 位の priority が **34 倍**離れている。これが recall の話より説得力のある事実で、製品の主張としても正しい: ripple が売っているのは「見つける」ことではなく **「読む順番を決める」** こと。

## 6. 特筆すべき強み

`docs/12-dogfood-log.md` の存在そのもの。中身の質が高い:

- headline 数値の leakage を自分で見つけ、holdout を実装し、**自分の主張を 34 pt 下げた**（`docs/12:11-36`）
- 「エッジが 1,299 に増えた、うち 769 が偽」を集計ではなく 1 箇所のスポットチェックで見つけた（`docs/12:55-71`）
- 「明らかに正しい」と思った変更が測ったら 6.7 pt 悪化したので revert し、**負の結果を記録として残した**（`docs/12:73-108`）
- oracle 構築で「3 回の false start は全部比較側の欠陥だった」と書いている（`docs/12:142-145`）

このログがあるだけで、レビュワーは他の主張も検証可能だと判断できる。§2 と §4 の指摘は全部この文化の上で直せるもので、設計の作り直しを要求するものは 1 つも無い。

## 7. 推奨アクション（順序つき）

1. **紹介ページの数値を差し替える**（P1）。撤回済みの値を公開し続けるのが一番安い失点。
2. **`.github/workflows/ci.yml` を追加**（P3）。`cargo build` / `clippy -- -D warnings` / `test`。手動保証をやめる。
3. **メトリクス改名**（P2 / P4）: `bug_density → fix_commit_ratio`、`untested → no_test_reference`、`ownership → author_concentration`（方向をコメントに明記し `docs/06:15` の記述と揃える）。risk 式を出す場所には未実装項の注記。
4. **`eval --oracle lsp` を TypeScript で回す**（P6）。tsserver / typescript-language-server 相手に、Elixir と同じ agreement 数値を出す。
5. **日本語の用語を直す**（P5）。日本語で出す資料は本文書 §2 の表に合わせる。
6. **`PROGRESS.txt` の stale な記述を落とす** — 40%、対応言語 3、44.5k/18k はすべて更新済みの値。docs/12 が正。

## 8. 実用性

### 8.1 サマリ

| 軸 | 評価 | 一言 |
|---|---|---|
| 技術的完成度 | **4 / 5** | 層の分離・決定性・劣化の申告まで含めて、v0 としては過剰に真面目 |
| 実用性（今日使えるか） | **3 / 5** | TS + Elixir のモノレポなら今日効く。それ以外は言語の壁 |
| 差別化（希少性） | **3.5 / 5** | co-change ではなく**サービス跨ぎの呼び出し連鎖**が本当の希少性 |
| 配布・導入 | **1 / 5** | バイナリ無し・`cargo install` 不可・LICENSE ファイル無し・Action 無し |
| 市場（単体製品として） | **2 / 5** | 単体の impact analysis は歴史的に製品化していない。隣接市場は全部誰かが埋めている |

### 8.2 速度は問題にならない

| 対象 | 実測 |
|---|---|
| hono 378 ファイル | cold 0.47 s / warm 0.33 s（release） |
| 実プロダクト 1,153 ファイル | cold 1.8 s（`docs/12:224`） |

概算 600〜800 ファイル/秒。**5 万ファイルのモノレポでも cold 60〜80 秒、warm は増分**なので、スケールが導入の障害になる可能性は低い。ここは心配する必要がない。

### 8.3 今日いちばん効くのは「絞り込み」

- `search` が候補を `kind` + `qualified` + `module` で構造化する（hono の `getPath` は 9 候補、うち 4 件が別クラスの同名メソッド）。エージェントが「たぶんこれ」で編集を始める確率を下げる効果は、今日そのまま出る。
- `review` の順序付け。1 位 101.34 / 6 位 2.96 の 34 倍差は、人間のレビュー時間の配分をそのまま変える。

この 2 つは co-change の強弱に依存しないので、§5 の訂正の影響を受けない。**実用性の芯はここ。**

### 8.4 律速は言語カバレッジ

4 言語（TS / Elixir / GraphQL / Rust）で、呼び出し解決が実用水準にあるのは TS と Elixir。世の中のリポジトリの多数派（Python / Go / Java / C#）が対象外。

ただしここは**構造的に安い**: Tier 0-1（シンボル抽出 + git overlay）は `.scm` + registry 1 行で足り、git 由来の信号はファイル粒度なので `review` は浅い対応でも動く（`docs/05:22`）。「対象リポジトリを 2 倍に広げるコストは 1 言語あたり数時間」というのは、この設計の一番効く性質。

### 8.5 運用の穴

- `reindex` が手動。ファイル監視もデーモンも無い（デーモンはロードマップ）。編集直後の `impact` は古い答えを返す。
- CI が無いので、headline のユースケース（PR レビューの絞り込み）が**そのままでは CI に乗らない**。
- エディタ統合が無い。`crates/lsp` は ripple が LSP を**使う**側で、ripple が LSP を**提供する**ものではない。

現時点の想定ユーザーは「CLI を叩ける人」+「MCP を設定できるエージェント」。それ以外の人の導線は無い。

### 8.6 n=1 の適合について

作者自身のスタック（TS フロント + Elixir バック + GraphQL + 別リポジトリ 2 本）に対して、この設計はぴったり噛み合っている。偶然ではなく、そこで価値が出るように作られている。**逆に言えば、その形をしていないチームでの価値はまだ検証されていない。** 2 社目の実データが最も情報量の多い次の一手。

## 9. マーケット

### 9.1 隣接する 3 つの市場と、それぞれの現実

**(a) AI エージェント向けのコード知識層（MCP）**

いま最も動きが速く、ripple の設計が向いている方向。ただし最大のリスクは**ハーネス側が内製で吸収すること**。Claude Code は grep + LSP を持ち、Cursor は独自インデックスを持つ。「grep で足りている」を超える証明が必要で、ripple の答えは 2 つある — **順序**（grep は順位を付けない）と**サービス跨ぎ**（grep は GraphQL op から Elixir resolver へ辿れない）。この 2 点に絞った説明をしないと、この市場では「もう 1 つのインデクサ」に見える。

**(b) レビュー対象の絞り込み（CodeScene の市場）**

実在して売れている市場。ripple の優位は関数粒度・OSS・エージェント接続。不利は、この市場が**エンタープライズ営業とダッシュボード/権限/監査**を要求すること。個人開発の延長で取れる市場ではない。

**(c) モノレポの affected set（Nx / Bazel / Turbo）**

CI の枠は既に埋まっている。関数粒度のリスクは直交する価値だが「置き換え」ではなく「追加」になるため、導入理由が弱い。

### 9.2 歴史的な補正

**単体の impact analysis は製品として成立した例がほぼ無い。** だから CodeScene や Sourcegraph の「一機能」になる。Sourcegraph 自身がコード検索からエージェント側へ軸を移している。**ripple がエージェント向けに寄せた読みは、この歴史に照らして正しい。**

### 9.3 希少性はどこにあるか

§5 の訂正後に残る、他が持っていないもの:

> **サービスとリポジトリを跨いだ呼び出し連鎖を、1 回の探索で返す。**
> `page.tsx → GraphqlCall → Absinthe resolver → context fn → DbQuery → Ecto schema`

静的解析ツールはリポジトリ境界で止まり、CodeScene は関数を指せず、Nx はビルドグラフしか見ない。ここは実際に空いている。**看板は co-change ではなくこれにすべき。**

ただし cross-service 解決はフレームワークごとの検出器が必要（Absinthe / Ecto は `elixir::dsl` にテーブルとして持つ設計）。これは**スケールの壁でもあり参入障壁でもある** — 一般化できない代わりに、真似するのも同じだけ面倒。

### 9.4 支払い意思

開発生産性ツールは、セキュリティ / コンプライアンスのフックが無いと予算が付きにくい。現実的な収益化の順序:

1. **自社（受託）の納品速度の差別化** — 一番確実。既に自分のスタックで動いている
2. **OSS + ポジショニング資産** — 技術的信用として機能する。`docs/12` の質はそのまま名刺になる
3. **PR bot の SaaS** — Action + ホスト型インデックスが前提。(1)(2) の後

「AI コーディングツールベンダーにインデックス層として売る」は理屈は通るが、彼らは内製する。期待値は低い。

## 10. 商品としての評価

**結論: ツールとしては credible な v0。製品としては配布が存在しない。**

### 10.1 製品として既にある性質（後付けが難しい部分）

MCP ネイティブ / トークン予算と `{shown, total}` / 劣化の申告 / 決定性 / `index-if-missing`。これらは後から入れると設計を壊すので、順序としては正しく作られている。

### 10.2 欠落（重い順）

| # | 欠落 | なぜ重いか |
|---|---|---|
| 1 | **配布が無い** | `version = "0.0.0"`、バイナリリリース無し、`cargo install` 不可。crate 名が `ir` / `parse` / `query` / `store` などの汎用語なので **crates.io に publish するには `ripple-*` への改名が前提**。導入の最大の障壁がここ |
| 2 | **LICENSE ファイルが無い** | `Cargo.toml` は `license = "Apache-2.0"` を宣言しているが、リポジトリにファイルが無い。GitHub がライセンスを検出できず、企業の依存審査で落ちる。**5 分で直る割に効果が大きい** |
| 3 | **PR Action が無い** | headline のユースケースが 5 行の YAML にならない。ここが最大レバレッジ |
| 4 | **ユーザー向けドキュメントが無い** | 設計文書 14 本に対して quickstart 0。README はアーキテクト向け。製品には「入れて 60 秒で価値が見える」導線が必要 |
| 5 | **名前** | `ripple` は Ripple / XRP と正面衝突して検索性が死んでいる。README も「Working codename … Final name TBD」と認めている。**公開前に決める**、後からの改名はコストが上がるだけ |
| 6 | 信頼の表層 | `serverInfo.version "0.0.0"`、CI バッジ無し、メトリクス名の過大主張（§2）。個々は小さいが「まだ製品ではない」という印象を作る |

---

## 11. 次の 5 手（レバレッジ順）

1. **LICENSE ファイル + crate 改名（`ripple-*`）+ GitHub Release のバイナリ** — 配布の穴を閉じる。ここが閉じるまで他の改善は届かない
2. **GitHub Action**（`ripple index` → `ripple review --json` → PR コメント）— headline のユースケースを YAML 5 行にする
3. **Python / Go を Tier 0-1 で追加** — 対象リポジトリを一気に広げる。コストは `.scm` + registry 1 行で、`review` は浅い対応でも動く
4. **名前を決める** — 公開の前。遅らせるほど高くつく
5. **看板を cross-service に差し替える** — co-change を主張から降ろし、「サービス跨ぎの連鎖 + 順序付け + エージェント接続」を前面に。§5 の訂正と §9.3 の希少性の両方に整合する

これらは全部、設計の作り直しを伴わない。**技術的な負債より、配布と物語の負債のほうが大きい。**
